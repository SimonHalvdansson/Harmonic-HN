# Harmonic palette extractor

Measured on 2026-09-05 on `emulator-5554`: Android API 37, x86_64,
`sdk_gphone16k_x86_64`, 1080 × 2424, 420 dpi. This follows the
[preview sampling investigation](preview-palette.md).

The replacement is enabled. Across two runs, complete uncached extraction was
**51–62% faster for the three preview images** and **36–48% faster for the logo**,
with no differences in the tested palette/tint outputs. The standalone quantizer
was 9.6–41.3× faster, but sampling and dispatch limit the full-pipeline gain.

**Dependency removal:** KMPalette has subsequently been removed from all runtime,
test, and benchmark dependencies. The comparison measurements below are historical;
current benchmarks exercise only Harmonic. Reference outputs were captured before
removal and are now fixed regression fixtures, rather than being regenerated by
the implementation under test.

## Implementation

`HarmonicPaletteExtractor` is a pure Kotlin specialization of KMPalette 4.0.0's
Apache-licensed quantizer and target selection. It accepts already-sampled ARGB
pixels, uses 16 colors and the default filter/targets, and preserves the ordered
swatches, populations, HSL values, and seven selected colors. It is not a general
replacement for custom KMPalette builders, filters, targets, regions, or resizing.

The app uses it for the existing 96 px preview, favicon, and fallback-painter
samples. Sampling and `PreviewTintPolicy` are unchanged. A local painter sampler
retains Main-thread rasterization and rounded 96 px dimensions; quantization uses
the existing four-job background gate. Settings and welcome previews also use
Harmonic, preserving their original 112² area limit, ceil-rounded dimensions,
and platform-native nearest-neighbor scaling. Resource decoding and extraction
use the same background gate. Source attribution remains in the license catalog.

Changes that reduce work:

- Reuse the 32,768-bin histogram and clear only touched bins, avoiding repeated
  128 KiB allocation and full scans through mostly empty bins.
- Calculate the default filter once for all 32,768 quantized colors, then use a
  shared lookup table.
- Use reusable primitive arrays for median-cut boxes, the heap, and sorting.
  Larger ranges use stable radix sorting of the complete channel key. Smaller
  ranges use the reference's channel permutation and primitive sort.
- Reuse the pixel readback buffer in a bounded pool of four exclusive workspaces.
  Cancellation returns slots, including cancellation of a suspended receiver.
- Calculate only the palette data the app consumes, without the general builder,
  target maps, or mutable library state objects.

The implementation deliberately retains volume ties in the heap, heap-array
iteration order, full secondary-channel sorting, exclusive-target order, Float
operation order, and ties-to-even rounding. These details affect the final tint.

The retained primitive storage is about 236 KiB per workspace, plus a shared
32 KiB filter table: about 1 MiB at the four-workspace bound, excluding small
objects. Returned palettes own their data and inputs are never modified.

## Exact-output validation

The original comparisons below used the actual KMPalette 4.0.0 library. Before
removing it, the core corpora were recorded as canonical FNV-1a fingerprints of
every output field and 18 final tints per image. Android fixtures were recorded
as SHA-256 fingerprints in `benchmark/src/main/assets/palette-goldens.txt`.
The Android fixtures cover all 29 preview sources and all six settings resources;
the preview hashes also include every sampled pixel. The capture-only code and
all library-backed benchmark methods were then removed.

- Desktop JVM tests exercise every quantized color in groups of 16, 1,200 seeded
  images, the complete color space in both orders, boundary cardinalities,
  skewed/equal populations, transparent/filtered colors, input immutability,
  capacity errors, and workspace reuse.
- Android runs **3,279 exact palette comparisons and 59,022 final tint checks**:
  29 real/generated bitmap fixtures, all quantized colors, 1,200 seeded images,
  and two full-color-space arrays. It compares ordered RGB/population pairs,
  bit-exact HSL floats, all seven targets, and 18 tint configurations per palette.
- The existing sampler equivalence test also passes: **116 pixel comparisons**
  across densities/directions and **2,088 tint configurations** checked through
  both production preview extraction and quantization of the real PainterLoader
  sample. Fixtures include RGB565, RGBA_F16, Display P3, transparency, odd aspect
  ratios, and tiny images that are upscaled.
- Another **600 concurrent production extractions** match their reference tints.
  Cancellation stress cancels 1,000 calls and verifies that subsequent extraction
  can still acquire the workspace and produce the expected palette.

All original comparisons passed. The retained tests now compare against the fixed
goldens and also check painter/bitmap sampling and concurrent/cancelled extraction.
This is strong differential evidence for the supported inputs, not
an exhaustive proof over every possible image. The cache result version and keys
remain valid because the tested outputs are identical.

## Timing method used for the original comparison

Both implementations ran in the same non-debuggable Android benchmark APK,
compiled with `cmd package compile -m speed -f`. Only the `EMULATOR` benchmark
warning is suppressed. No Gradle builds run during the timed comparisons.

`HarmonicPaletteBenchmark` isolates the quantizer on identical pre-sampled pixels.
The reference mutates its input, so the benchmark refreshes its reusable input
array outside measurement. The replacement reuses its workspace. Neither path
gets an extraction-result cache hit.

`HarmonicPalettePipelineBenchmark` compares a frozen copy of the pre-replacement
bitmap pipeline against the production extractor. Both include identical
`runBlocking`/Main entry scaffolding, the four-job Default dispatcher gate, fresh
96 px sampling, pixel readback, palette generation, and final tint calculation.
The replacement additionally includes its actual workspace pool overhead.

Every iteration performs extraction. Images are already decoded, and the lookup
table/workspaces are warm after benchmark warmup. Thus “cold extraction” means
**a tint-cache miss**, not a fresh process. Downloading, decoding, recomposition,
and drawing frames are outside these timings. No app-data or tint-cache clearing
is needed because both measured functions bypass the caches.

### Startup and limits

In separate fresh instrumentation processes, the first extraction includes
workspace allocation, class initialization, and the shared lookup-table build.
The three measurements were 1.88/2.23/1.64 ms for Harmonic and 1.68/2.10/1.63 ms
for KMPalette. These single-shot probes are noisy; they show that the first call
does not receive the large steady-state speedup. Initialization stays off Main.

The benefit applies to actual extraction, especially bursts of different images.
Already-cached tints receive no speedup. These are emulator measurements and do
not establish a physical-device speedup or a scrolling FPS/jank improvement.

## Running the retained regression tests and benchmarks

The old-vs-new timings above were collected before removing the old dependency.
The current checkout retains the measured values and current-implementation
benchmarks, but deliberately does not contain an executable old-library baseline.

Use Android Studio's JBR for Gradle. On this Windows host:

```powershell
$env:JAVA_HOME = 'C:/Program Files/Android/Android Studio1/jbr'
$env:PATH = "$env:JAVA_HOME/bin;$env:PATH"
./gradlew.bat :benchmark:assembleBenchmarkBenchmark
```

Deploy and compile the benchmark APK, substituting the authorized device serial:

```text
android install --device=emulator-5554 --apks=benchmark/build/outputs/apk/benchmarkBenchmark/benchmark-benchmarkBenchmark.apk
adb -s emulator-5554 shell cmd package compile -m speed -f com.simon.harmonichackernews.benchmark
```

Run `HarmonicPaletteFirstUseTest` alone in a fresh instrumentation invocation.
For equivalence, select `HarmonicPaletteEquivalenceTest,PreviewPaletteEquivalenceTest`.
For timing, select `HarmonicPaletteBenchmark,HarmonicPalettePipelineBenchmark`.
Class names must each use the `com.simon.harmonichackernews.benchmark.` prefix:

```text
adb -s emulator-5554 shell am instrument -w -r -e class <fully-qualified-classes> -e androidx.benchmark.suppressErrors EMULATOR -e additionalTestOutputDir /sdcard/Download/harmonic-palette-results com.simon.harmonichackernews.benchmark/androidx.benchmark.junit4.AndroidBenchmarkRunner
```

Use a separate output directory for each run. The output includes
`com.simon.harmonichackernews.benchmark-benchmarkData.json` with distributions,
medians, minimums, and allocation counts.

Passed `:core:compileCommonMainKotlinMetadata`, `:core:desktopTest` (529 tests),

and `lintDebug`. iOS compilation/runtime validation is unavailable on this
Windows host.
