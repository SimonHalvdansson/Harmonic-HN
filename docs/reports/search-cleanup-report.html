01 / The scope

Cleanup with a concrete payoff

Your request was to look for ways to simplify the app and improve its code. I inspected shared presentation logic, search, submissions, settings, data storage, and loading helpers. Search stood out because several small pieces of duplication also made request ownership harder to follow.

The changes are concentrated in core/src/commonMain, where Android, iOS, and desktop share their application logic. The resulting code has one place to start a search load, one place to finish it, and one cancellation helper used when replacing or restoring a search.

Code cleanup

Make the existing rules easier to maintain

Use Kotlin’s data-class copying for state updates, reuse the existing error policy, consolidate loading paths, and express sorting with comparator builders.

Behavior improvements

Fix the boundaries between requests

Reject obsolete results after restoration, honor the “Newest” option in history search, limit simultaneous history lookups, and refuse pagination after results are exhausted.

Across the three production files, the patch adds 115 lines and removes 141: a net reduction of 26 lines. The new test file adds 243 lines. The meaningful improvement is fewer places that must agree on the same behavior.

02 / State & loading

One loading path, one completion path

Previously, loadMore() updated the result limit and loading flags itself, then called execute(loadMore = true, publishLoading = false). A normal search let execute() set those flags. That extra boolean meant a caller had to know whether the loading work had already been done.

Now loadMore() checks whether another load is allowed and delegates to execute(loadMore = true). The executor calculates the request’s result limit and publishes the loading state in one place.

Step 1StartCancel the previous load and capture the new generation.
Step 2PrepareChoose the result limit and set the loading flags.
Step 3ResolveProduce a SearchResult from success or an ordinary failure.
Step 4PublishReject an obsolete generation, then apply one completion update.

Success and failure use the same finishing logic

The old try and catch branches each checked the generation, cleared the job reference, and reset loading flags. Both now produce a SearchResult. A single block checks whether that result still belongs to the active request and publishes it.

On a “load more” failure, the result retains the currently displayed stories. Cancellation is still rethrown as CancellationException, so stopping a coroutine does not become a normal search error.

State updates use the data class directly

The previous publish() helper repeated ten state fields as parameters with defaults, then copied those fields into a new StorySearchUiState. Adding a new field meant maintaining another parallel list. The new helper accepts an update such as copy(options = currentOptions()), using the copy function Kotlin generates for the data class.

The helper still makes a list copy and increments the revision counter. These preserve the existing list-container ownership and change-notification behavior; this is not a deep copy of every Story.

See the new state-update helper 
private inline fun publish(update: StorySearchUiState.() -> StorySearchUiState) {
    val current = state.value
    val next = current.update()
    mutableState.value = next.copy(
        stories = next.stories.toList(),
        revision = current.revision + 1,
    )
}

// Example call site:
publish { copy(options = currentOptions()) }

Error classification has one source

The private Throwable.toStoryLoadFailure() in the search store duplicated StoryFeedRefreshPolicy.failureFor(). I removed the duplicate and reused the policy: HTTP 404 maps to “not found,” HTTP 429 to “rate limited,” and other errors to “general.” The classification stays the same, while future changes only need to be made once.

03 / Correctness

Restored results stay restored

A request receives a generation number when it starts. Before publishing, it checks that its generation still matches the store’s current number. The old code already used this protection when starting a new search, but restore() did not invalidate the previous request.

That left a specific race: restore a saved search while an older request is pending, then let that older request finish. Its generation still looked current, so it could replace the restored content.

Before
  1. Search A begins with generation 7.
  2. Saved search B is restored. Generation stays 7.
  3. A finishes and passes the generation check.
A can overwrite B’s restored results.
After
  1. Search A begins with generation 7.
  2. Restoring B cancels A and advances the generation to 8.
  3. A’s late result carries generation 7 and is rejected.
B’s restored state remains intact.

A shared cancelLoad() now increments the generation, cancels the previous job, and clears its reference. It is used by cancel(), restore(), and execute().

See the cancellation helper and the stale-result guard
private fun cancelLoad() {
    generation++
    loadJob?.cancel()
    loadJob = null
}

// restore() calls cancelLoad() before restoring options and results.
// After a request resolves, execute() checks:
if (requestGeneration != generation) return@launch

Why cancel and check a generation? Cancellation asks old work to stop. The generation check prevents a late result from being applied even if that work does not cooperate. The regression test deliberately uses a continuation that can finish after cancellation, then asserts that the entire restored state is unchanged.

04 / Resource usage

History search has a concurrency limit

“Only clicked” search loads stories from the saved history IDs. Previously, it started one async coroutine for each ID, with no limit around repository requests. A long history could therefore attempt many story lookups at once.

I added a store-owned Semaphore(8). Each lookup must acquire a permit through withPermit, and releases it when the lookup completes, fails, or is cancelled. Work waiting for a permit can proceed when a slot becomes available.

Illustrative workload, not a benchmark. The limit applies to history lookups in one StorySearchStore.

Result handling is easier to follow

awaitAll() replaces the manual list of deferred results followed by map { it.await() }. Results remain associated with the original ID order before sorting; completion order does not choose the displayed order.

The filter adapter is created once for the result list instead of once per story. The complete-failure rule is expressed directly with outcomes.all(ClickedStoryLoad::failed). A story that cannot be found is still different from a thrown request failure, successful partial results are still kept, and an empty history returns an empty result without an error.

See the bounded request structure

This abbreviated example shows where the permit sits. The production block also records success and ordinary failures for each story.

private val clickedStoryRequests = Semaphore(MAX_CONCURRENT_HISTORY_REQUESTS)

val outcomes = ids.map { id ->
    async {
        clickedStoryRequests.withPermit {
            // Fetch the story and record its outcome here.
            // CancellationException is rethrown.
        }
    }
}.awaitAll()

private companion object {
    const val MAX_CONCURRENT_HISTORY_REQUESTS = 8
}

Tradeoff: Eight is an explicit engineering limit, not a measured optimum. It reduces simultaneous lookups, but does not guarantee faster searches. The code still creates one coroutine per history ID and waits for all outcomes; this change does not introduce a history cache, incremental results, or a fixed-size worker pool.

05 / Readability & behavior

Sorting rules are explicit

“Newest” now means publication time

The old sortOnlyClickedResultsIfNeeded() only sorted when the selection was “Relevance.” Selecting “Newest” left results in the incoming history order, which reflects visits rather than necessarily reflecting when stories were published.

I renamed the function to sortOnlyClickedResults() and added a descending sort on Story.time for the “Newest” branch. Relevance still uses the existing relevance scorer.

The relevance comparator reads like its specification

The previous comparator had a handwritten conditional branch for each tie-breaker. The replacement uses Kotlin comparator builders in the same order: relevance score, points, comment count, publication time, then original position. All are descending except original position, which preserves input order for exact ties.

Relevance comparator after cleanup
scoredStories.sortWith(
    compareByDescending<ScoredStory> { it.relevanceScore }
        .thenByDescending { it.story.score }
        .thenByDescending { it.story.descendants }
        .thenByDescending { it.story.time }
        .thenBy { it.originalIndex },
)

The scoring formula itself is unchanged, and each story is still scored once before sorting. The existing relevance test verifies ranking and original-order preservation for ties. I also shortened the history title-match check to a single nullable expression that still rejects missing titles.

06 / Request boundaries

Stop when there are no more results

The old loadMore() guard rejected calls while loading or without a request, but did not inspect canLoadMore. Even after the repository returned fewer results than requested, another call could increase the limit and make another request.

Before / actual guard
if (state.value.loading || request == null) return
After / actual guard
if (state.value.loading ||
    !state.value.canLoadMore ||
    request == null) return

The executor also captures hitsPerPage for the request and passes it to loadAlgoliaStories(). Both URL construction and the “can load more?” decision use that same value, rather than rereading mutable state after the network call.

Pagination still follows the raw response count

The search asks Algolia for an expanding result window: 200 results, then 400, and so on. It replaces the returned list rather than requesting a separate numbered page. The cleanup preserves that contract.

A response containing 200 stories may leave only one visible after user filters. The raw count still permits another request. The new test checks exactly that case, confirms existing rows stay visible during loading, then verifies that a short response stops further pagination. A separate test confirms that top-story searches keep their original time cutoff when the result limit grows.

07 / Evidence

A few terms used in this report

Coroutine: a unit of asynchronous work. Generation: a counter identifying which request is still current. Semaphore: a fixed set of permits that limits simultaneous work. Regression test: a repeatable check that a bug stays fixed or an existing behavior survives a refactor. StateFlow: the observable holder of the current search state.
